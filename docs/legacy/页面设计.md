## 2. 「我的栏」= 一个布尔组合单元（这次是重点）

### 2.1 数据模型

**每一个自定义栏是一个独立单元**：有自己的名字、条件树、命中集合、命中数量。
可以有任意多个（不是"筛选开关键"，也不是一个全局筛选器）。

```jsonc
Column {
  id, name, color, order,
  expr: Node,               // 布尔表达式树
  count: 88,                // 缓存的命中数
  count_dirty: false,       // 是否需要重算
  created_at, updated_at
}

Node = Group { op: "AND" | "OR" | "NOT", children: [Node...] }
     | Cond  { field: "model", op: "contains", value: "Anima*" }
```

- 根节点固定是 Group；`NOT` 组只有一个子节点（UI 上叫"反选组"）
- 组可以任意嵌套，AND/OR/NOT 混用，等价于把 `(A AND B) OR (C AND NOT D)` 这种式子存下来
- 编辑页底部实时显示**等价表达式**，防止语义和你想的不一样

### 2.2 条件字段（全部可选，不是只有画师串）

| 分组 | 字段 | 支持的算子 |
| --- | --- | --- |
| 内容 | 模型 / LoRA / 采样器 / 步数 / CFG / 种子 / 分辨率 / 宽高比 | `= ≠ ~ !~ ≥ ≤ 在区间内` |
| 提示词 | 提示词 / 负面提示词 / 提示词长度 / 角色 / 画师 / 标签 | `包含 不包含 = ≠ 为空 非空` |
| 我的 | 评分 / 收藏 / 批注 / 自建标签 | `= ≥ ≤ 包含` |
| 文件 | 文件夹 / 文件名 / 日期 / 文件大小 / 格式 | `= 包含 在区间内` |
| 状态 | 有工作流 / 有提示词 / 已删除 / 相似图组 | `是 否` |

**"画师串"不需要单独的字段。** 你说的场景就是「提示词 包含 `<那一整串>`」：

- 匹配发生在**归一化后的 token 序列**上（去权重、反转义、下划线↔空格、小写），
  所以 `jinx \(league of legends\)` / `jinx_(league_of_legends)` / `Jinx (League of Legends)`
  会命中同一条
- 画师在这个库里主要有三种写法，实测都存在（691 张命中画师的图里）：

  | 写法 | 例 | 图片数 |
  | --- | --- | --- |
  | `@名字` / `artist:名字`（NoobAI/Illustrious 习惯）| `@nixeu`（106）、`artist:betabeet`（32）| **360** |
  | 裸 tag（danbooru 画师表里的词）| `yoneyama_mai`（77）、`remsrar`（89）、`wlop`（48）| **201** |
  | 同一张图两种都写 | — | 130 |

  三种都归一到"画师"这个字段，所以你可以直接 `画师 = nixeu`，不用记他当时怎么写的。

## 3. 命中数量：入库时增量算 + 缓存

目标规模 **5 万张起步、10 万张不降级、20 万张能用**。

### 3.1 存什么

```
image(id, path, folder_id, w, h, bytes, mtime, model, sampler, steps, cfg, seed,
      pos_prompt, neg_prompt, pos_len, has_workflow, has_prompt, rating, deleted, hash)
image_tag(image_id, tag, kind)      -- kind: character / artist / general / custom
column(id, name, expr_json, count, expr_version, dirty)
column_hit(column_id, image_id)     -- 命中集合，用 Roaring Bitmap 落盘
stat_tag(tag, kind, pos_count, neg_count, rating_sum, rating_n)
```

### 3.2 什么时候算

| 事件 | 动作 | 成本 |
| --- | --- | --- |
| 新图入库 | 解析 → 写 image/image_tag → **对每个栏求值一次** → 写 column_hit → `count±1` | 单张 < 20 ms |
| 改评分 | 只重算「条件里引用了评分」的栏（字段→栏的反向依赖表）| 单张 < 5 ms |
| 改栏条件 | 只重算这一栏，`expr_version+1`，count 重算 | 4,508 张 0.3 s；10 万张 ≈ 3 s（后台跑，先显示旧值+转圈） |
| 删图/恢复 | 从所有 column_hit 里摘掉/加回，count±1 | O(栏数) |
| 全量重建 | 导入完成后后台顺序跑一遍，可断点续 | 10 万张约 1 分钟 |

- **不做"每次进页面重算"**，也不给所有条件组合预建缓存（组合爆炸）
- 栏的命中集合直接就是中间网格的数据源，翻页只是 bitmap 取第 N 段 → 不查 SQL
- 统计页（词频/角色分布）在**打开时按当前条件实时聚合**（10 万张 ≈ 1 s），
  只有"全库无条件"的统计走 `stat_tag` 预聚合表

### 3.3 一致性

- 计数和 bitmap 在同一事务里写；中途崩溃只会让 `dirty=1`，下次启动补算
- 计数滞后时显示旧值 + 淡淡的"重算中"，不阻塞浏览

## 4. 正负面提示词识别（已实测，不是纸上算法）

### 4.1 实测结果（你的 4,508 张）

| 指标 | 结果 |
| --- | --- |
| 有效图片 | 4,508（另有 131 张已删除、1 张无 API 图）|
| 识别出正向提示词 | **4,218（93.6%）** |
| 识别出负向提示词 | **4,047（89.8%）** |
| 正负都有 | 4,047 |
| 没识别出正向的 290 张 | **全部是 SeedVR2 放大/重绘管线**（`LoadImage → ImageScaleBy → SaveImage` 或 `UNETLoader → SeedVR2VideoUpscaler`），本来就没有提示词；逐张查过，没有任何节点带文本字段 |
| 修复的一个隐藏 bug | 反向遍历时如果穿过**同时有 `positive`/`negative` 两个入口的节点**（`ToBasicPipe`、`UltimateSDUpscale`、`FaceDetailer`），会把两条文本都收进同一个角色 → 2,495 张正负串位。修法：按角色只跟同名口子 |

**结论：有提示词的图，正负面识别率是 4,218 / 4,218 = 100%。** 剩下的不是漏识别，是无提示词。

实测的文本来源节点类型（这就是需要支持的形态）：

| 正向来源 | 张数 | 负向来源 | 张数 |
| --- | --- | --- | --- |
| `PrimitiveStringMultiline` | 2,607 | `PrimitiveStringMultiline` | 2,598 |
| `CLIPTextEncode` | 1,470 | `CLIPTextEncode` | 2,546 |
| `StringConcatenate` | 1,056 | `StringConcatenate` | 801 |
| `ShowText\|pysssss` | 35 | `Efficient Loader` | 16 |
| `Eff. Loader SDXL` | 1 | `Eff. Loader SDXL` | 1 |

> 踩到的坑：Efficient Nodes 的 `Efficient Loader` 把正负提示词存成**节点上的字符串**，
> 而不是接到采样器；提示词还经常由 `StringConcatenate(string_a, delimiter, string_b)` 拼出来。
> 只按"采样器的 positive/negative 入口往回走"会漏掉 340 张。

### 4.2 算法

```
① 找种子（谁规定了正负角色）
   · 任意节点输入 positive → 正向种子；输入 negative → 负向种子
     - 值是链接：从该节点往上追（KSampler.positive → ControlNetApply.positive → …）
     - 值是字符串：这个节点自身就是文本源（Efficient Loader 这类）
   · BasicGuider.conditioning → 正向（SamplerCustomAdvanced 的写法）
② 从种子反向遍历到文本源
   · 到节点先问"你能产出文本吗"：text / text_g / text_l / value / string / prompt
   · 拼接类节点（StringConcatenate / StringFunction）按 string_a + delimiter + string_b 求值
   · 不跟进 model / clip / vae / latent / image / pipe 这些口子（跟进去会跑到加载器上）
   · 深度上限 25，visited 去重（图里大量共享节点和环）
③ 兜底：没有 positive/negative 入口的图（纯 Flux 之类）
   取全部文本源，类名带 neg 的算负向，只有一条文本的算正向
④ 内嵌负面块：正向文本里出现 `Negative prompt:` / `【负面】` 就从中劈开
```

### 4.3 归一化（给筛选和打标用）

```
去 <lora:...>  →  去 (xxx:1.2) 权重（支持一层嵌套）  →  反转义 \( \)  →
去纯强调括号 (sunbeam) / (full_body)  →  抽 @名 / artist:名 前缀  →
name(series) → name_(series)  →  空格→下划线、小写
```

实测提示词形态（4,218 张有正向的）：

| 形态 | 张数 | 影响 |
| --- | --- | --- |
| 含中文 | 1,054（25.0%）| 自然语言，不能只按逗号切 |
| 带转义括号 `\(` | 1,177（27.9%）| 就是角色/作品名，必须反转义否则全错 |
| 带权重 `(x:1.2)` | 283 | 不去权重会得到 `(x:1.2)` 这种垃圾 token |
| 含 `BREAK` | 8 | 当逗号处理 |
| token 数 ≤3 / 4-10 / 11-30 / 31-80 / >80 | 1,010 / 257 / 1,410 / 1,408 / 133 | 一半以上是大段堆词 |
| 本地词表能认识的 token | 69,485 / 112,847 = **61.6%** | 剩下是不规范写法、中文、自创词 |

### 4.5 顺带查出来的一个数据问题：1,419 张的负面 = 正面

| | 张数 | 说明 |
| --- | --- | --- |
| 负面 ≈ 正面（Jaccard > 0.6）| **1,419（35%）** | 同一个 `CLIPTextEncode` 同时接正负，或负面节点复制了正面文本 |
| 干净负面 | 1,972 | 计入上面的负面统计 |

这不是解析错——逐张看过多张图，图上确实是一个 CLIPTextEncode 同时喂 KSampler 的
positive 和 negative，或者两个节点文本一模一样。存成 `image.neg_is_dup` 标记：

- 默认**不计入**负面统计（否则 `1girl`/`solo` 会冲进负面榜单，全是假的）
- 标签页给一个「数据体检：1,419 张的负面提示词与正面相同」入口，点进去能看到是哪几个工作流干的
- 这是个顺手白送的功能：它直接告诉你哪个 ComfyUI 工作流接错了

所以流程是：**danbooru 导出当主词表**（带类别/别名/中文名）→

## 10. 右键 → 处理（RTX VSR）

### 10.1 入口

| 位置 | 操作 |
| --- | --- |
| 查看器里右键图片 | 菜单第一项 `RTX VSR 超分处理…`（Ctrl+U）|
| 网格里右键缩略图 | 同一个菜单 |
| 查看器右下「处理」卡片 | 常驻按钮，不用记右键 |
| 多选后右键 | 菜单变成"处理 N 张"，进同一个队列 |

### 10.2 能力检测（必须先做）

启动时跑一次，结果缓存到设置里，可手动「重新检测」：

```
显卡存在？ → 是 NVIDIA RTX 20 系及以上？
   → 驱动 ≥ 535？
      → VSR SDK 可加载？
         → 全部通过：菜单项可用
         → 任一失败：菜单项【置灰】+ 悬浮说明具体原因
                       （"当前显卡 GTX 1660 不支持 RTX VSR" / "驱动 512.xx 太旧，需要 ≥535"）
```

**不许静默失败**：不支持就明确置灰并说明，不要让用户点了没反应。

### 10.3 参数（档位按你的要求统一）

| 项 | 值 | 是否可改 |
| --- | --- | --- |
| 画质档位 | **HIGHBITRATE + ULTRA** | **锁定**，设置页只读展示 |
| 放大倍数 | 2× / 4× | 可改，默认 2× |
| 4× 显存不足 | 拒绝并提示"需要约 X GB 显存，当前可用 Y GB" | — |
| 输出方式 | 另存副本并入同一堆叠（默认）/ 覆盖原件（先备份）/ 另存到指定文件夹 | 可改 |
| 保留 | 原图的提示词、工作流、评分（继承）| 勾选 |

界面上把 HIGHBITRATE + ULTRA 画成两个**不可点的胶囊**，旁边标「已锁定」，
让人一眼看出"这不是我漏了选项，是设计如此"。

### 10.4 执行

- **单并发**（VSR 吃满显存），其余进队列；队列可取消、可移除、失败可重试
- 处理在后台跑，**不阻塞浏览**；完成时托盘气泡 + 网格角标变「已处理」
- 结果图带 `processed` 标记和 `source_id`，**自动加入原图所在的相似图组**，方便并排看
- 预估：2× 单张约 1.8 秒、显存约 3.2 GB（按 1024×1536 输入估）

### 10.5 对比页

处理完直接进对比（`05-compare.png`）：左右两张、缩放平移联动、
顶部显示分辨率/体积/耗时变化，底部三选一 **保留 / 丢弃 / 再处理一次（4×）**。

### 10.6 为"以后加更多功能"留的口子

右键菜单里是**「处理 ▸」子菜单**，现在只有 RTX VSR 一项：

```
处理 ▸
  ├ RTX VSR 超分…          ← MVP 只有这个
  ├ （将来）Real-ESRGAN 超分
  ├ （将来）去噪 / 去水印
  └ （将来）抠图导出
```

代码上所有处理器实现同一接口，菜单和队列与具体处理器解耦：

```ts
interface ImageProcessor {
  id: string;                 // "rtx-vsr"
  name: string;               // "RTX VSR 超分"
  probe(): Capability;        // 支持/不支持/原因
  options(input: ImageMeta): Option[];   // 该处理器自己的参数
  run(job: Job, ctx: Context): Promise<Result>;
}
```

加新功能 = 加一个实现 + 一行注册，菜单/队列/对比页/角标全都不用改。

## 11. UI/UX 要点（逐页优化清单）

### 11.1 十条原则

1. **主流程一屏完成**：浏览 → 打分 → 放大 → 处理，不跳页。查看器是"中间区域放大"，不是新窗口。
2. **键盘优先**：`←/→` 切图、`空格` 预览/关闭、`1-5` 打分、`0` 清分、`Ctrl+U` 处理、
   `T` 加标签、`Del` 删除、`Ctrl+F` 筛选。所有快捷键在菜单里标出来，用户能自己发现。
3. **三态设计**：每个列表都要有 **空 / 加载 / 错误** 三种样子。空态给"下一步做什么"，不要只写"暂无数据"。
4. **状态永远可见**：导入中、栏重算中、处理中，都在角标/状态条上显示，不弹模态框。
5. **不打断**：处理、导入、重算全在后台；完成用托盘气泡，不抢焦点。
6. **可撤销**：删除进回收站；处理默认保留原图；覆盖原件前强制备份。
7. **条件编辑器只有一套**：总览的条件、栏的条件、搜索的高级筛选，都是同一个 `Node` 树组件。
   学一次，到处能用。
8. **密度可调**：网格缩略图 4 档（现在的滑杆），2000 张和 20 张都能看舒服。
9. **信息分层**：缩略图角标最多 2 个（最有用的），其余进详情；不要把 8 个标签糊在图上。
10. **说清边界**：不支持的按钮置灰 + 说明原因；不假装能用。

| **体检** | 负面=正面的 1,419 张、无提示词 290 张、未评分 3,293 张 |

**排行是这次的重点**：它回答的是"什么词/角色/画师/模型出好图"，而不是"什么词出现得多"。
表格列 = 名称 · 张数 · 平均分（带星）· ≥4★ · 评分分布条；
**只统计出现 ≥5 张的条目**，避免"1 张 5★"冲上榜首。

### 12.8 等价表达式（只给开发看）

条件树的内部表示就是一棵 `Node` 树，渲染成中缀式即可，不需要用户在界面上看到：

```
模型 ~ Anima*  AND  正向提示词 ~ silver hair
AND ( 正向提示词 ~ night  OR  正向提示词 ~ starry sky  OR  模型 !~ NoobAI )
```

- 运算符：`AND` / `OR` / `NOT`（NOT 组只有一个子节点）
- 字段算子：`~` 包含、`!~` 不包含、`=` `!=`、`>=` `<=`、`in` 区间
- 序列化：`column.expr_json` 存整棵树；求值时对每张图深度优先求值，遇 AND 短路

## 13. v0.6.2：始终使用 RTX VSR + 元数据永不删

### 13.1 右键加一项「始终使用 RTX VSR」

```
右键 ─┬─ RTX VSR 处理…      Ctrl+U
      ├─ 显示原图            Esc
      ├─ ☑ 始终使用 RTX VSR        ← 新增，勾选态记在本地
      ├─ 复制…
      ├─ 清除评分
      └─ …
```

勾上之后：**切到下一张图也自动套 VSR**，看图下方状态胶囊同时点亮勾，
再点一次「始终使用 RTX VSR」取消。这个开关是**本次运行有效**（和"不落盘"一致），
退出后回到设置里的默认值。查看器状态胶囊：`☑ RTX VSR 2× | 显示原图`。

### 13.2 处理一律不回写图库

- 不在 ComfyUI 里后处理再保存（你的决定），App 自己也不回写 `output` 目录
- 处理结果只在内存/临时目录，**绝不参与入库、不参与统计、不进文件夹树**
- 只有设置里显式选「保存到库」才落盘，且落在 App 自己的 `post/` 目录，**不碰 `output`**
- 理由就是你提的：一旦把后处理图混进 output，文件夹树、去重、统计全乱

### 13.3 元数据永远不删（核心决定）

**数据库是唯一真相，磁盘上的文件只是"当前有没有原图"的一种状态。**

```
image.file_state ∈ { present, missing, deleted }
```

| 事件 | 数据库 | 磁盘 |
| --- | --- | --- |
| 你在资源管理器里把图删了 | 下次扫描发现文件不在 → `missing`，**记录全保留** | 文件没了 |
| 你在 App 里删 | 标 `deleted`，文件进回收站（可恢复）| 进回收站 |
| 清空回收站 | `deleted` 保持 | 真没了 |
| 重新把同一个文件放回去 | 按内容哈希认出 → 恢复 `present`，评分/标签/批注全在 | 有 |

所以：

- 删图**不会**让评分、提示词、角色、画师、批注、相似图组消失
- 统计默认排除 `deleted`，但**能一键包含**（否则"我删了多少、删的是什么风格"就没法算）
- 筛选里有 `已删除` 字段；左栏第二块底部给一个 `已删除 131` 入口，随时能翻回去看
- 相似图组不会因为删掉几张就断链——靠 `dHash`（64 bit）+ 时间 + 提示词相似度维持

### 13.4 低清缩略图：实测 + 决策

**A. 老库现成的 `thumbnail.avif`（640×640，AVIF）**

| 指标 | 值 |
| --- | --- |
| 张数 | 4,639 |
| 合计 | **157.2 MB** |
| 平均 / 中位 / p90 | 34.7 KB / 29.8 KB / 60.3 KB |
| 外推 10 万张 | **≈ 3.3 GB** |

**B. 用你库里的原图现场编码（250 张样本）**

| 规格 | 每张 | 1 万 | 5 万 | 10 万 | 20 万 |
| --- | --- | --- | --- | --- | --- |
| 短边 128 · WebP q60 | 3.9 KB | 38 MB | 191 MB | **382 MB** | 764 MB |
| **短边 160 · WebP q60** | **5.5 KB** | 53 MB | 267 MB | **533 MB** | 1.0 GB |
| 短边 160 · WebP q75 | 6.4 KB | 63 MB | 313 MB | 626 MB | 1.2 GB |
| 短边 256 · WebP q70 | 12.3 KB | 120 MB | 598 MB | 1.2 GB | 2.3 GB |
| 短边 256 · JPEG q75 | 17.6 KB | 172 MB | 859 MB | 1.7 GB | 3.4 GB |
| 短边 320 · WebP q70 | 17.1 KB | 167 MB | 833 MB | 1.6 GB | 3.3 GB |

**C. 元数据本身也不是零成本**（实测老库）

| 内容 | 平均每张 | 10 万张 | 备注 |
| --- | --- | --- | --- |
| `data.json` 元数据 | 0.8 KB | 80 MB | |
| `data-ai.json` 工作流 | **13.5 KB** | 1.3 GB | gzip 后只剩 **25%** → **330 MB** |
| 提示词 + 结构化字段 | ≈0.5 KB | 50 MB | 进 SQLite |

### 13.5 结论：留

**每张永久留存成本 ≈ 10 KB**（0.5 KB 结构化 + 0.4 KB 提示词 + 3.4 KB 工作流 gzip + 5.5 KB 缩略图 + 32 B dHash）

| 张数 | 元数据 + 低清缩略图 |
| --- | --- |
| 1 万 | ≈ 100 MB |
| 5 万 | ≈ 500 MB |
| **10 万** | **≈ 1.0 GB** |
| 20 万 | ≈ 2.0 GB |

10 万张一共 1 GB，换"删了的图仍然能被搜到、被统计、被回看"，这个账很划算。

**具体规格**

| 用途 | 规格 | 每张 | 生命周期 |
| --- | --- | --- | --- |
| 网格缩略图 | 短边 320 · WebP q70 | 17.1 KB | **缓存**，可随时从原图重建，LRU 上限 2 GB |
| 归档缩略图（已删除 / 缺失）| **短边 160 · WebP q60** | **5.5 KB** | **永久保留**，从网格缩略图降采样生成，不重新读原图 |
| 相似图签名 | dHash 64 bit + 主色 4×3 | 32 B | 永久 |

- 归档缩略图**只在文件被判定为 `missing`/`deleted` 的那一刻生成**（从已有 320 缩略图缩到 160），
  不额外读原图，一张 < 5 ms
- 设置里给开关：`为已删除图片保留低清预览（约 5.5 KB/张）`，默认**开**
- 关掉的话，已删除条目在图墙里显示成占位块，但元数据、统计、筛选照旧

## 14. v0.6.3：统计的三处调整

### 14.1 门槛可调

统计页顶部（范围栏右侧）加了 `门槛  [≥3] [≥5] [≥10] [全部]`，默认 ≥5 张。
它同时作用于概览的三张表和排行页的整张表——样本太小的条目直接不参与排名，
避免"1 张 5★"冲榜。这个值记在本地设置里。

### 14.2 角色 / 画师 / 正向 tag 三类分开

概览底部原来是两张"正向 tag"卡（数量一张、影响一张），**现在拆成三张，一类一张**：

| 卡 | 条目数 | 内容 |
| --- | --- | --- |
| 角色 | 190 个 | jinx 482 张 · 1.9★ · 1.2× |
| 画师 | 128 位 | nixeu 120 张 · 2.6★ · 1.6× |
| 正向 tag | 6,938 种 | 1girl 2,098 张 · 1.5★ · 0.9× |

角色和画师**不再混进 general tag 里算**——它们的口径本来就不一样
（角色按 danbooru category=4 命中，画师按 category=1 或 `@name` 写法命中），
混在一起排行会出现"jinx 排第 5、1girl 排第 1"这种没意义的对比。

### 14.3 张数和对评分影响放同一张表

每张卡的列固定为：**名称 · 张数 · 平均分 · lift**

- `lift = 该条目的平均分 / 全库已评分平均分（1.6）`
- ≥1.15× 绿、≤0.85× 橙、中间灰——一眼看出"这个词是加分还是减分"
- 排行页保留更细的表：名称 · 张数 · 平均分（带星）· lift（中轴双向条 + 倍数）· ≥4★ · 评分分布条，
  维度可在 角色 / 画师 / 提示词 / 模型 之间切，排序可在 lift / 张数 / 平均分 之间切

### 14.4 四个页签的最终分工

| 页签 | 干什么 |
| --- | --- |
| 概览 | KPI 6 个 + 评分分布 + 月度产出 + **角色/画师/tag 三张合并表** |
| 排行 | 四维度 × 三种排序的完整表，带分布条 |
