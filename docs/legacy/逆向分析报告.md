# 鲸鱼图库 1.0.25 逆向分析报告

> 目标：软件已停更，评估能否自行继续开发 / 修补。
> 结论：**能，而且改造点比想象的多。** 但要分清三层，难度差一个数量级。

---

## 一、技术画像

| 项目 | 值 |
| --- | --- |
| 产品 | 鲸鱼图库 (WhaleLibrary) v1.0.25 |
| 运行时 | Electron **34.5.8** / Chromium 132.0.6834.210 |
| 构建 | electron-vite（`out/main`、`out/preload`、`out/renderer`） |
| 保护 | **bytenode**：主进程与 preload 编译成 V8 字节码 `.jsc` |
| asar | 12.66 MB，1362 个文件（1345 打包 + 17 unpacked） |
| 数据层 | 纯 JSON 文件（`data.json`、`tags.json`、`folderStore.json`、`imageContent.json`、`whalepkData.json`、`workflow.json`、`data-ai.json`） |
| 授权 | `jsonwebtoken` + `node-machine-id` + Electron `safeStorage` 加密本地令牌 |

目录结构：

```
resources/app.asar
├─ package.json          main = ./out/main/index.js
├─ out/main/
│   ├─ index.js          72 B  →  require(loader) + require(index.jsc)
│   ├─ bytecode-loader.cjs   bytenode 加载器
│   └─ index.jsc         129,800 B  ← 真正的业务代码（字节码）
├─ out/preload/          6 个窗口各一份，同样全是 .jsc
├─ out/renderer/         index.html 91 KB + assets/index-*.js 166 KB（压缩未混淆）
│   └─ page-{about,activeMgmt,feedback,openUpdate,serialActive,start}/
├─ node_modules/         sharp / tencentcloud-sdk / jsonwebtoken / electron-conf …
└─ resources/            图标、托盘、默认图库
```

**关键点：三层里只有主进程是字节码，界面层是普通 JS。**

## 三、三层可行性

### 1. 界面层 renderer —— 完全可改（推荐主战场）

- `index.html` 91 KB + 6 个子页面，标准 DOM 操作（不是 Vue）。
- `assets/index-B1kZZY6I.js` 166 KB，**压缩但未混淆**：变量被改成 `e/t/n/o`，但函数名（`aiTag`、`goPage`、`state`）、字符串、`ipcRenderer.invoke("通道名")` 全部保留。
- 改法：格式化后直接改，或用 `document.addEventListener` 追加脚本；重打包或直接跑源码目录都行。
- 能改什么：布局、交互、排序/筛选、空状态、图片卡片、色板、提示文案、右键菜单……**所有"看得见的没完善"都在这一层**。

### 2. preload —— 可改，但通常不用动

只有 6 个 `.jsc`（index/about/activation/activeMgmt/serialActive/updateWindow）。它只是把 `ipcRenderer` 桥接给页面；要加新通道，在主进程加 handler 即可，preload 可以不动（页面里直接用现有桥的对象）。

### 3. 主进程 main —— 字节码，不能直接读，但能"包起来"

`index.jsc` 是 V8 code cache，**源码文本不在里面**（bytenode 用小技巧把源长度写进头部，加载时用等长空白串占位）。所以：

- ❌ 不能用 VSCode 改、不能 `console.log` 断点到源码行；
- ✅ **函数名、字符串常量全部保留**——我已经捞出 598 个标识符：`handleSerialCodeVerify`、`verifyLocalToken`、`encryptWithSafeStorage`、`handleWindowsFileCopy`、`exportMaterialPack`、`refreshLibraryCache`、`getAuthDeviceArr`、`createNewLibrary`、`buildWindowsMenu` …
- ✅ **IPC 契约完整可得**：从 renderer 里直接读到 53 个通道名（`activeData`、`copyPrompt`、`exportMultipleImages`、`rightClick-menu`、`updateWindow-update` …）。这是主进程对外暴露的全部接口。

**改主进程的三条路：**

| 路线 | 做法 | 成本 | 适合 |
| --- | --- | --- | --- |
| **A. 探针/包装**（推荐） | 用我们自己的 `index.js` 先接管 `ipcMain`，再 `require("./index.jsc")`。记录、改写返回值、拦截、追加新通道 | 低 | 加功能、改行为、修 bug |
| B. 字节码反汇编 | 解析 V8 13.2 的 SerializedCodeData，还原成指令级伪代码 | 高（研究级，V8 13.x 无成熟工具） | 只想"读懂"某段逻辑 |
| C. 整体重写 | 丢掉 `.jsc`，按 IPC 契约重写主进程 | 很高 | 完全不想要原逻辑 |

路线 A 的样例已经放好：`out/main/mods/ipc-logger.js`，把 `out/main/index.js` 改成三行即可（文件头有说明）。它能把每个通道的入参、耗时、返回值写进 `<userData>/ipc-calls.log`——**跑一遍点几下，主进程的秘密基本就摊开了**，比硬啃字节码高效得多。

## 四、工作流（不碰安装目录）

```powershell
# 1. 改代码
notepad _work\app\out\renderer\assets\index-B1kZZY6I.js

# 2. 跑起来看效果（独立 user-data，和已装版本互不干扰）
_work\run-portable.cmd

# 3. 满意了，回写到安装目录（先备份！）
node _work\pack-asar.mjs _work\app resources\app.asar.new
Copy-Item resources\app.asar resources\app.asar.bak-1.0.25
Move-Item resources\app.asar.new resources\app.asar -Force
```

打包器会把 `sharp` 的 `.node/.dll` 自动标成 unpacked 并放到 `app.asar.unpacked`，原生模块照常加载。

> 若便携副本起不来：把 `_work\portable\resources\app` 这个目录联接换成真实目录
> （`mklink /J` 在部分环境不支持），即把 `_work\app` 整个拷进去。

## 五、已经能看到的"没完善"

| 现象 | 证据 | 影响 |
| --- | --- | --- |
| **自动更新是死的** | `app-update.yml` → `https://example.com/auto-updates` | 更新窗口、`checkForUpdates` 都在，但永远拉不到包 |
| 浏览器插件功能半成品 | `page-start/start.html` 里 360 浏览器那项整体被注释掉，图标文件也没进包 | 「插件安装引导」少一个入口 |
| 窗口按钮脚本缺失 | `page-about` 里 `windowsBtn.js` 注释掉且未打包 | 关于窗口靠 preload 兜底 |
| 遗留未完成的初始化 | `index.html` 里 `initialization-indexedDB.js` 被注释 | 说明原计划用 IndexedDB，后来改成 JSON 存储 |
| 关于页是模板残留 | `page-about/index.html` 的 `<title>Document</title>`、`lang="en"` | 纯观感 |
| CSP 很松 | `img-src 'self' data:` 之外没限制 | 加自定义样式/图片时不用改 CSP，方便 |

另外：**构建本身是完整的**——7 个 HTML 的 75 个活引用全部命中，没有断链。（我第一版审计报了 4 处缺失，核实后确认全部是被注释掉的死代码，不算 bug。）

数据全是 JSON，所以你库里的标签、评分、文件夹结构都能直接读改写，甚至可以写脚本批量修数据/迁移格式——这块没有任何门槛。

## 六、边界

- 自己的机器、自己用、自己改：没问题，这也是「软件停止维护后用户自救」的常规做法。
- 但**不要分发改过的安装包**（原作者的著作权仍在），也**不要动授权那一套**（`jsonwebtoken` + `node-machine-id` + `safeStorage` 校验）——这部分我不参与。
- 官方若日后更新，覆盖安装会冲掉你的修改；`resources\app.asar` 记得留备份。

## 七、下一步选一个方向

- **A（推荐）**：先跑 `run-portable.cmd` 确认能起，然后挂上 `ipc-logger`，点几下界面收集真实 IPC 流量；同时把 renderer 格式化，从最简单的 UI/交互补起。
- **B**：直接告诉我想先修哪个具体问题（比如「更新器指向 example.com，我想让它能装我自己的补丁」），我按最小改动出补丁。
- **C**：想彻底掌握主进程逻辑，我再评估做 V8 13.2 字节码反汇编的可行性（工作量大，先给结论再动手）。
